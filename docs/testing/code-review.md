## 1. რას ვამოწმებ (checklist)

- [ ] **სისწორე:** აკეთებს თუ არა კოდი იმას, რასაც User Story და Given/When/Then მოითხოვს? გათვალისწინებულია საზღვრის შემთხვევები (0, 1, max, max+1, null, ცარიელი სია)?
- [ ] **ტესტები:** არის unit-ტესტი ახალ ლოგიკაზე? AAA სტრუქტურა? ტესტის სახელი ამბობს, რას ამოწმებს?
- [ ] **უსაფრთხოება:** ვალიდაცია სერვერზეა (და არა მხოლოდ ფორმაში)? ავტორიზაცია ამოწმებს მფლობელს/როლს? პაროლი ჰეშირებულია? SQL injection გამორიცხულია?
- [ ] **ერთდროულობა:** შეიძლება ორმა მოთხოვნამ ერთად დაარღვიოს წესი (check-then-act)?
- [ ] **წაკითხვადობა:** სახელები, ფუნქციის ზომა, დუბლირება, magic numbers.
- [ ] **შეცდომების დამუშავება:** გასაგები შეტყობინება მომხმარებლისთვის, სწორი HTTP სტატუსი.

## 3. მაგალითი — როგორი უნდა იყოს კომენტარები

(ტიპური პრობლემები, რომლებიც ხშირად გვხვდება სტუდენტურ პროექტებში — გამოიყენეთ ნიმუშად, როცა სხვა გუნდის PR-ს ნახავთ.)

> 🔴 **`TransferService.cs:42` — check-then-act race condition.**
> ჯერ ბალანსს ამოწმებთ, მერე ცალკე ჩანაწერით აკლებთ. ორი პარალელური გადარიცხვა ორივე გაივლის შემოწმებას და ბალანსი უარყოფითი გახდება. შემოთავაზება: ერთი ატომური `UPDATE Accounts SET Balance = Balance - @amount WHERE Id = @id AND Balance >= @amount` და შეამოწმეთ affected rows, ან ტრანზაქცია `Serializable` იზოლაციით. დაამატეთ integration-ტესტი ორი პარალელური მოთხოვნით.

> 🟡 **`GradeCalculator.cs:18` — საზღვრის შემთხვევა არ არის დაფარული.**
> `score > 90` ნიშნავს, რომ ზუსტად 90 ქულა `B`-ს იღებს, თუმცა სპეციფიკაციით `A` არის 90–100. შემოთავაზება: `score >= 90` და `[InlineData(89, "B")] [InlineData(90, "A")]` ტესტები.

> 🟢 **`CourseRegistrationTests.cs:55` — ტესტის სახელი არაინფორმაციულია.**
> `Test3()` არაფერს ამბობს. შემოთავაზება: `Register_WhenTotalCreditsWouldExceed30_ReturnsLimitError`, და დაყავით `// Arrange / Act / Assert` ბლოკებად.
